# Контракт API

Все даты — UTC. Денежные значения `price_minor` и `total_price_minor` — целые копейки, валюта RUB. Бронирование имеет UUID, рейс — положительный int64. `user_id` — строка внешнего идентификатора пользователя. Контакт пассажира фиксируется в конкретной брони.

## REST

| Метод | Путь | Результат |
|---|---|---|
| GET | `/flights?origin=SVO&destination=LED&date=2026-12-01` | Массив SCHEDULED-рейсов; дата необязательна |
| GET | `/flights/{id}` | Объект рейса |
| POST | `/bookings` | Созданная бронь, HTTP 201 |
| GET | `/bookings/{id}` | Объект брони |
| GET | `/bookings?user_id=student-1` | Массив бронирований пользователя |
| POST | `/bookings/{id}/cancel` | Отменённая бронь |

Тело создания:

```json
{"user_id":"student-1","flight_id":1,"passenger_name":"Ivan Petrov","passenger_email":"ivan@example.com","seat_count":2}
```

Создание: GetFlight → ReserveSeats → INSERT CONFIRMED. `total_price_minor` сохраняется как снимок `seat_count × price_minor` из GetFlight. Отмена: проверка CONFIRMED → ReleaseReservation → UPDATE CANCELLED. Повторная REST-отмена возвращает 409. Отсутствующая бронь — 404, неверный JSON — 422. Ошибки содержат `detail`.

## gRPC

Контракт: `proto/flight.proto`, сервис `flight.v1.FlightService`. Все методы требуют metadata `x-api-key`, равную `FLIGHT_API_KEY` из окружения сервера.

| Метод | Вход | Поведение |
|---|---|---|
| SearchFlights | origin, destination, необязательный departure_date | Только SCHEDULED; Timestamp даты должен быть полночью UTC |
| GetFlight | id | Рейс, включая время, цену, количество мест и статус |
| UpdateFlight | id, необязательные price_minor и status | Изменение цены и/или статуса; нужен хотя бы один изменяемый атрибут |
| ReserveSeats | flight_id, seat_count, booking_id | Атомарное резервирование; тот же UUID и параметры возвращают существующую ACTIVE-резервацию |
| ReleaseReservation | booking_id | Атомарный возврат мест; повтор возвращает RELEASED без изменения счётчика |

UpdateFlight меняет только цену и статус рейса. Он не отменяет существующие брони автоматически; их отмена выполняется через Booking.

Повтор ReserveSeats с другим flight_id/seat_count — ALREADY_EXISTS. Повтор после RELEASED/EXPIRED — FAILED_PRECONDITION: места заново не резервируются. Состояние EXPIRED предусмотрено контрактом, автоматического истечения нет.

| gRPC code | Причина | REST |
|---|---|---:|
| INVALID_ARGUMENT | Неверные параметры | 422 |
| NOT_FOUND | Нет рейса или резервации | 404 |
| RESOURCE_EXHAUSTED | Недостаточно мест | 409 |
| FAILED_PRECONDITION | Рейс не SCHEDULED или резервация уже не ACTIVE | 409 |
| ALREADY_EXISTS | UUID резервации использован с другими параметрами | 409 |
| UNAUTHENTICATED | Отсутствующий, неверный или дублированный API key | 502 |
| UNAVAILABLE | Недоступен сервис/его БД | 503 |
| DEADLINE_EXCEEDED | Истекло время ожидания | 504 |
| INTERNAL | Ошибка операции БД | 502 |

Booking повторяет RPC только для UNAVAILABLE и DEADLINE_EXCEEDED: всего до 3 попыток с паузами 100 и 200 мс. Параметры и UUID не меняются. Встроенные retry gRPC отключены. Ошибка межсервисного ключа отображается как 502, потому что это ошибка конфигурации сервиса, а не credentials REST-клиента.

## Кеш

Cache-Aside: Redis GET → при miss SQL → Redis SET с TTL. Ключи `flight:{id}` и `search:{origin}:{destination}:{date|all}` имеют TTL 300 секунд. Попадания и промахи журналируются как `cache hit` / `cache miss`.

ReserveSeats, ReleaseReservation и UpdateFlight сохраняют изменение данных и увеличение версии в одной транзакции PostgreSQL. Пока удерживается блокировка версии, приложение удаляет Redis-ключи перед COMMIT. Redis не участвует в PostgreSQL-транзакции: при откате БД удалённый кеш просто заполняется заново. Общая блокировка версии предотвращает гонку с заполнением кеша. Значение Redis содержит версию; при чтении она сравнивается с БД. Даже если Sentinel повысил отставшую реплику, устаревшее значение не выдаётся клиенту. Эта схема сохраняет один короткий SQL-запрос при cache hit и сериализует изменения; она рассчитана на небольшой проект.

Если Redis недоступен, запрос обслуживается из PostgreSQL. Неудавшееся физическое удаление не делает старое значение допустимым: его версия больше не совпадает. Все Redis-значения имеют TTL. Прямое изменение таблиц SQL вне сервиса требует обновления `cache_state` и инвалидирования.

Топология: мастер + реплика + три Sentinel с quorum 2. Клиент redis-py использует SentinelConnectionPool и читает только мастер. Sentinel и Redis сохраняют конфигурацию ролей в томах, чтобы переживать перезапуски после failover. Узлы кеша имеют фиксированные адреса в отдельной сети и записи extra_hosts: остановка контейнера не вызывает зависания DNS в Sentinel. По умолчанию сеть — 172.30.93.0/24; при конфликте с существующей сетью её префикс меняется через REDIS_SUBNET_PREFIX. Порты Redis, Sentinel, PostgreSQL и Flight наружу не публикуются. TLS и пользовательская REST-аутентификация не входят в реализацию.

## Границы транзакций

Изменение мест и резервации атомарно в Flight-БД. Если ReserveSeats завершился ошибкой, Booking не вставляется. После ошибки INSERT Booking выполняется компенсирующий ReleaseReservation. Повторяемое резервирование уменьшает риск потерянного ответа, но не создаёт распределённую транзакцию.

Падение Booking между успешной резервацией и записью брони может оставить резервацию без брони. При потере ответа COMMIT исход неизвестен; UUID записывается в лог для сверки, автоматическое освобождение в этом случае не выполняется. После успешного освобождения и неудачной записи CANCELLED повторная отмена исправляет состояние. Если все попытки RPC и компенсация не удались, требуется сверка данных двух БД. Глобальная атомарность при произвольных сбоях не гарантируется.
